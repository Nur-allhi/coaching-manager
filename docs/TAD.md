# TAD — Technical Architecture Document

**Status:** live · **Target skill:** `senior-backend`

How the system is built. _Why_ the product exists is in [`PRD.md`](PRD.md). _What is allowed_
is in [`SECURITY.md`](SECURITY.md). Code conventions live in
[`REPO_RULES.md`](REPO_RULES.md).

## 1. Shape

A local-first single-page app. One device, one browser tab, one SQLite database file in the
browser's OPFS storage. No server, no account, no sync, no runtime network call.

```
React UI                 src/app, src/modules/*
  │  TanStack Query (reads, optimistic writes)
Module services          src/modules/*/services
  │  Zod validation · permission checks · business rules
Repositories             src/modules/*/repositories
  │  hand-written parameterized SQL, one table family per module
Db client                src/core/db
  │  one promise queue · tx() holds the queue until commit
Web Worker               src/core/db/worker
     @sqlite.org/sqlite-wasm · OPFS · opfs-sahpool VFS
```

## 2. Rules of the layering

1. UI code MUST NOT contain SQL. It goes through module services.
2. A module MUST NOT read another module's tables. It imports that module's public
   `index.ts`.
3. Read-model modules (`dashboard`, `reports`, `leaderboard`) MAY read any table, but only
   from files inside their own `queries/` folder, and they MUST NOT write.
4. `src/core/*` MUST NOT import from `src/modules/*`.
5. `src/components/ui/*` is generated by the shadcn CLI and MUST NOT be hand-edited.

Reason: the boundaries are what make eleven modules behave like one codebase, and what make
the blast radius of a change computable before it is made.

## 3. The `Db` contract

```ts
export interface Db {
  query<T>(sql: string, params?: unknown[]): Promise<T[]>
  run(sql: string, params?: unknown[]): Promise<{ changes: number }>
  tx<T>(fn: (t: Db) => Promise<T>): Promise<T>
  exportBytes(): Promise<Uint8Array>
  importBytes(bytes: Uint8Array): Promise<void>
}
```

- **Serialization.** The client funnels every call through one promise queue, so a
  transaction can never interleave with another statement.
- **`tx(fn)`** holds the queue for the duration of `fn`. If `fn` throws, the transaction rolls
  back and the queue is released. Nothing outside sees uncommitted rows.
- **One interface, two runtimes.** The browser runs sqlite-wasm; Vitest runs `better-sqlite3`
  behind the same interface, so repository tests exercise real SQL in milliseconds.

## 4. Storage

| Concern     | Decision                                                                                                                                  |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Engine      | SQLite compiled to WebAssembly (`@sqlite.org/sqlite-wasm`)                                                                                |
| Host        | A dedicated Web Worker. The UI thread never blocks on SQLite.                                                                             |
| VFS         | `opfs-sahpool`. Needs no COOP/COEP headers, so any static host works.                                                                     |
| Persistence | The database file lives in OPFS. `navigator.storage.persist()` is requested on first run; the status is shown in Settings.                |
| Concurrency | `navigator.locks.request('app-db-owner', { ifAvailable: true })`. The sahpool VFS allows one connection, so a second tab MUST be refused. |
| Pragmas     | `PRAGMA foreign_keys = ON` at open. WAL is NOT used with this VFS.                                                                        |

## 5. Data model

### 5.1 Common columns

Every business table carries the same five columns:

| Column       | Type                         | Meaning                                         |
| ------------ | ---------------------------- | ----------------------------------------------- |
| `id`         | `TEXT PRIMARY KEY`           | UUIDv7. Time-sortable, never reused.            |
| `created_at` | `INTEGER`                    | Epoch milliseconds, UTC.                        |
| `updated_at` | `INTEGER`                    | Epoch milliseconds, UTC. Bumped on every write. |
| `deleted_at` | `INTEGER \| NULL`            | Epoch ms of soft delete. `NULL` means alive.    |
| `version`    | `INTEGER NOT NULL DEFAULT 1` | Incremented on every update.                    |

### 5.2 Column conventions

| Kind      | Convention                         | Example                             |
| --------- | ---------------------------------- | ----------------------------------- |
| Money     | `INTEGER`, column ends in `_minor` | `amount_minor`                      |
| Boolean   | `INTEGER` 0 or 1                   | `is_current`, `absent`              |
| Date      | `TEXT` `YYYY-MM-DD`                | `admitted_on`, `held_on`            |
| Month     | `TEXT` `YYYY-MM`                   | `charges.month`                     |
| Timestamp | `INTEGER` epoch ms UTC             | `created_at`, `audit_log.at`        |
| Enum-ish  | `TEXT` with a documented value set | `status`, `method`, `discount_kind` |
| Reference | `TEXT` + `REFERENCES other(id)`    | `student_id`                        |

### 5.3 Rules

1. Money MUST be an integer number of paisa. A float MUST NOT appear in a money column, a
   money parameter, or a money calculation.
2. Percent discounts MUST be rounded exactly once, at the end, to the nearest paisa.
3. Soft delete only. Every default list query filters `deleted_at IS NULL`.
4. Every update goes through `repo.update(id, patch, expectedVersion)`. A version mismatch
   MUST abort the write.
5. Deleting a parent that still has children MUST be refused with a message the admin can
   read.

### 5.4 Tables

```sql
CREATE TABLE app_meta(key TEXT PRIMARY KEY, value TEXT NOT NULL);
CREATE TABLE settings(key TEXT PRIMARY KEY, value TEXT NOT NULL, updated_at INTEGER NOT NULL);
CREATE TABLE counters(name TEXT PRIMARY KEY, value INTEGER NOT NULL);

CREATE TABLE academic_years(COMMON, name TEXT NOT NULL, starts_on TEXT NOT NULL,
  ends_on TEXT NOT NULL, is_current INTEGER NOT NULL DEFAULT 0);
CREATE TABLE classes(COMMON, name TEXT NOT NULL, sort_order INTEGER NOT NULL DEFAULT 0);
CREATE TABLE subjects(COMMON, name TEXT NOT NULL, code TEXT);
CREATE TABLE batches(COMMON, academic_year_id TEXT NOT NULL REFERENCES academic_years(id),
  class_id TEXT NOT NULL REFERENCES classes(id), name TEXT NOT NULL,
  days_mask INTEGER NOT NULL,          -- bit 0 = Sunday ... bit 6 = Saturday
  start_time TEXT NOT NULL, end_time TEXT NOT NULL, room TEXT,
  capacity INTEGER, monthly_fee_minor INTEGER NOT NULL,
  status TEXT NOT NULL DEFAULT 'active');

CREATE TABLE students(COMMON, student_no TEXT NOT NULL UNIQUE, full_name TEXT NOT NULL,
  gender TEXT, dob TEXT, phone TEXT, guardian_name TEXT, guardian_phone TEXT,
  address TEXT, school_name TEXT, admitted_on TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'active',   -- active | dropped | passed_out
  notes TEXT);
CREATE TABLE enrollments(COMMON, student_id TEXT NOT NULL REFERENCES students(id),
  batch_id TEXT NOT NULL REFERENCES batches(id), enrolled_on TEXT NOT NULL, left_on TEXT,
  admission_fee_minor INTEGER NOT NULL DEFAULT 0, monthly_fee_minor INTEGER NOT NULL,
  discount_kind TEXT NOT NULL DEFAULT 'none',  -- none | fixed | percent
  discount_value INTEGER NOT NULL DEFAULT 0,
  status TEXT NOT NULL DEFAULT 'active');

CREATE TABLE charges(COMMON, enrollment_id TEXT NOT NULL REFERENCES enrollments(id),
  student_id TEXT NOT NULL REFERENCES students(id), month TEXT,   -- YYYY-MM, NULL for one-off
  kind TEXT NOT NULL,                      -- admission | monthly | other
  description TEXT, amount_minor INTEGER NOT NULL, discount_minor INTEGER NOT NULL DEFAULT 0,
  UNIQUE(enrollment_id, month, kind));
CREATE TABLE payments(COMMON, receipt_no TEXT NOT NULL UNIQUE,
  student_id TEXT NOT NULL REFERENCES students(id), paid_on TEXT NOT NULL,
  method TEXT NOT NULL DEFAULT 'cash', amount_minor INTEGER NOT NULL, note TEXT,
  status TEXT NOT NULL DEFAULT 'valid',    -- valid | void
  revision INTEGER NOT NULL DEFAULT 0);
CREATE TABLE payment_allocations(payment_id TEXT NOT NULL REFERENCES payments(id),
  charge_id TEXT NOT NULL REFERENCES charges(id), amount_minor INTEGER NOT NULL,
  PRIMARY KEY(payment_id, charge_id));

CREATE TABLE attendance_sessions(COMMON, batch_id TEXT NOT NULL REFERENCES batches(id),
  held_on TEXT NOT NULL, UNIQUE(batch_id, held_on));
CREATE TABLE attendance_records(session_id TEXT NOT NULL REFERENCES attendance_sessions(id),
  student_id TEXT NOT NULL REFERENCES students(id),
  status TEXT NOT NULL,                    -- P | A | L | E (present, absent, late, excused)
  PRIMARY KEY(session_id, student_id));

CREATE TABLE exams(COMMON, batch_id TEXT NOT NULL REFERENCES batches(id),
  subject_id TEXT REFERENCES subjects(id), name TEXT NOT NULL, held_on TEXT NOT NULL,
  full_marks REAL NOT NULL, pass_marks REAL NOT NULL);
CREATE TABLE exam_results(exam_id TEXT NOT NULL REFERENCES exams(id),
  student_id TEXT NOT NULL REFERENCES students(id), marks REAL, absent INTEGER NOT NULL DEFAULT 0,
  remark TEXT, updated_at INTEGER NOT NULL, PRIMARY KEY(exam_id, student_id));

CREATE TABLE audit_log(id TEXT PRIMARY KEY, at INTEGER NOT NULL, user_id TEXT,
  entity TEXT NOT NULL, entity_id TEXT NOT NULL,
  action TEXT NOT NULL,                    -- create | update | delete | restore | void
  before_json TEXT, after_json TEXT, undone INTEGER NOT NULL DEFAULT 0);
```

`exam_results.marks` is the one deliberate `REAL`: exam scores are not money.

### 5.5 Required indexes

`students(full_name)`, `students(phone)`, `enrollments(student_id)`,
`enrollments(batch_id)`, `charges(student_id, month)`, `payments(student_id, paid_on)`,
`attendance_records(student_id)`, `exam_results(student_id)`, `audit_log(entity, entity_id)`.
FTS5 over student name, phone, guardian name and student number lands in P2-3.

### 5.6 Derived rules

These live once, in the owning module, and are reused everywhere.

| Quantity         | Formula                                        |
| ---------------- | ---------------------------------------------- |
| Charge net       | `amount_minor - discount_minor`                |
| Paid on a charge | sum of allocations for **valid** payments      |
| Due on a charge  | `net - paid`                                   |
| Advance          | payment amount not yet allocated to any charge |

- A voided payment keeps its row and its receipt number; its allocations stop counting.
- Monthly charges are generated idempotently. `UNIQUE(enrollment_id, month, kind)` is the
  guard, not a "was this generated" flag.
- A payment's allocations MUST NOT sum to more than the payment amount.
- Editing a payment amount re-runs allocation inside one transaction, increments `revision`
  and keeps the receipt number.

### 5.7 Ranking and grades

- Competition ranking (1, 2, 2, 4) via `RANK() OVER (PARTITION BY scope ORDER BY total_marks DESC)`.
- Scopes: per exam, per month, per academic year; filtered by batch or class.
- An absent student counts as 0 in totals, is flagged, and is excluded from averages
  (`absent_counts_as_zero` setting).
- The grading scale lives in `settings` and is editable. Default: A+ 80–100 (5.00), A 70–79
  (4.00), A- 60–69 (3.50), B 50–59 (3.00), C 40–49 (2.00), D 33–39 (1.00), F below 33 (0).

### 5.8 Identifiers

- Primary key: UUIDv7 via `uuidv7`, generated by one `newId()` helper in `src/core/db`.
- Student number: `YYYY-0001` by admission year.
- Receipt number: `R-YYYY-000001`, sequential, never reused, never changed by an edit.
- Sequences come from the `counters` table, allocated inside the same transaction as the row
  that uses them, so they stay gapless.

### 5.9 Dates

Stored as `YYYY-MM-DD` (dates), `YYYY-MM` (months) and epoch milliseconds UTC (timestamps).
Displayed in **Asia/Dhaka**. "Today" means today in Dhaka. Arithmetic uses `date-fns`.

## 6. Schema versioning and migrations

- `app_meta.schema_version` is the single source of truth for the persisted schema version.
- Migrations are append-only. A shipped migration MUST NOT be edited.
- Filenames: `YYYYMMDDHHmm_<module>_<description>.sql`, ordered by the UTC timestamp.
- Each module contributes its own migrations; the runner applies them in filename order.
- A migration runs inside a transaction, after a pre-migration snapshot. A failure rolls back
  and the app offers Restore and Export.
- Every migration MUST have a test that upgrades a fixture database from each earlier
  version.
- A schema change is at least a MINOR release (see [`VERSIONING.md`](VERSIONING.md)).

## 9. API surface

There is no network API. The product's "API" has exactly two boundaries:

1. **The worker RPC boundary** — Comlink over a `MessagePort`. The surface is the `Db`
   interface in §3.
2. **The module service boundary** — the only thing UI code may call.

Both are in-process and typed. There is no HTTP, no URL routing for data, and no cache to
invalidate server-side. `PLAN.md` §10 forbids it and the e2e suite enforces it.

## 10. Events

A tiny typed event bus carries domain notifications, mostly to invalidate TanStack Query
caches:

```ts
type DomainEvent =
  | 'student.updated'
  | 'student.deleted'
  | 'enrollment.updated'
  | 'payment.created'
  | 'payment.updated'
  | 'payment.voided'
  | 'charge.generated'
  | 'attendance.saved'
  | 'exam.result.saved'
  | 'settings.updated'
```

Modules MUST publish events rather than reaching into another module's query cache.

## 11. Client state

| Concern           | Tool                                      | Rule                                                |
| ----------------- | ----------------------------------------- | --------------------------------------------------- |
| Server state      | TanStack Query                            | Every read is a query; every write is a mutation.   |
| Optimistic writes | one shared `useOptimisticMutation` helper | Roll back on error, refetch on settle.              |
| Tiny UI state     | Zustand                                   | Filters, dialogs, table density. Nothing else.      |
| Form state        | React Hook Form + Zod                     | Validate at the boundary, and again in the service. |

Optimistic updates MUST NOT touch derived values — receipt numbers, ranks, dues. Those appear
only after the transaction commits.

## 12. Audit and undo

Every create, update, delete and void writes an `audit_log` row in the same transaction as the
change, holding the full before and after row snapshots as JSON.

- Undo applies the inverse and writes a _new_ audit entry. History is never rewritten.
- Each record has a History tab that lists its audit entries and can restore a version.

## 13. Backup, restore and export

- A snapshot is `exportBytes()` of the live database, written to OPFS as
  `/backups/YYYYMMDD-HHmmss_reason.sqlite` with a `.json` sidecar (reason, schema version,
  SHA-256, size, row counts). Reasons: `auto`, `manual`, `pre-restore`, `pre-migration`,
  `pre-import`.
- Rotation keeps the newest 10.
- Restore validates before it touches anything: checksum, open in a temporary in-memory
  database, `PRAGMA integrity_check`, and a schema version not newer than the app's. A
  pre-restore snapshot is taken first. If any step fails, the live database is untouched.
- File export/import writes a portable `.sqlite` file, optionally AES-GCM encrypted, using
  `showSaveFilePicker` where available and a normal download elsewhere.
- Backup file format carries its own `format_version`, separate from `schema_version`.

The procedure in `PLAN.md` §7.3 is authoritative and MUST NOT be changed without the human.

## 14. Printing and export

- PDF is produced by **printing**: `/print/*` routes render clean HTML with `@page` CSS and
  call `window.print()`. The browser shapes Bangla conjuncts correctly; JavaScript PDF
  libraries do not reliably.
- Excel is ExcelJS, CSV is PapaParse. CSV is written UTF-8 **with BOM** so Excel opens Bangla
  correctly.
- Every export uses the filters the user is looking at.
